Add retry with backoff to api-client

PR #482 · feat/client-retry → main · 2 files · +58 −9 · reviewing for correctness and failure behaviour

Motivation

Payments calls fail transiently under load (about 0.4% of requests, mostly 503s from the gateway). Today every failure surfaces to the caller. This PR wraps request() in a retry loop with exponential backoff and jitter, opt-in per call.

Where to focus

  1. Which errors are retried (note 2).
  2. The idempotency guard (note 3).
  3. Timeout budget across attempts (note 4).

1nit

retryOn receives unknown, so every caller has to narrow. Consider typing it as (err: ApiError | Error) => boolean since request() only throws those.

2blocking

Default retries everything, including 400s, auth failures, and JSON parse errors. A 401 will be retried three times with backoff and then fail anyway, and a 409 on a payment will be retried into a duplicate. Default should be: network errors, 408, 429, 502, 503, 504. Make callers opt in to anything wider.

6praise

Full jitter (0.5 to 1.5× the delay) rather than fixed steps. This is the version that actually spreads retries out under a thundering herd.

3blocking

Retry is on by default for every method. A POST /charges that times out after the server committed will be re-sent. Either default retry to false for non-idempotent methods, or require an Idempotency-Key header before retrying a POST. The payments service is the stated motivation, so this is the case that matters.

4question

The 8 s timeout is per attempt, so three attempts plus backoff can take about 27 s. Is that intended? The gateway's own upstream timeout is 30 s, which leaves almost no margin. A total budget (deadlineMs) that shrinks the per-attempt timeout would be safer.

5nit

retry ?? {} means "undefined and null both retry with defaults." Fine, but say so in the RequestOptions doc comment; the | false union makes it look like the only way to opt out.

Verdict: request changes

The mechanics are right (jitter, cap, cleanup in finally). The policy is wrong: retrying everything by default, including non-idempotent writes, is the one thing this change must not do on a payments path. Two changes and this is good to merge:

  • Narrow the default retryOn to network errors and 408/429/502/503/504.
  • Default retry to off for POST/PATCH/DELETE unless an idempotency key is present.
